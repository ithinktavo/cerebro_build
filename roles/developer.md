# Playbook: developers

Your code stays in GitHub. The vault is two things. It is your own notebook, and it is the context every AI tool reads before it touches a repository: where the code is, how to run it, what was decided and why, and where you left off. It links to commits, pull requests, issues, and tracker items by URL and never copies them.

## What to tell the AI in your profile

The build prompt, [prompts/build-work-vault.md](../prompts/build-work-vault.md), starts with a profile. A developer fills in:

- Roles: developer, tech lead, or architect. Any of these, or one named repository, turns on the Developer module, the `Repos/` folder.
- Repositories, one line each: local path and GitHub URL.
- Projects, one line each: name, goal, and which repositories they touch.
- Trackers: GitHub Projects (owner and project number), Jira (site, and whether you use `acli` or `jira`), or Azure DevOps (organization and project), and which tools you are signed in to from the terminal.
- The tools that read the folder (Claude Code, Codex, GitHub Copilot CLI, GitHub Copilot in VS Code) and the chat tools you also use.
- Whether you lead a team or owe a report upward. Either one adds the Teams or Reports module to the same vault.
- The one thing you are tired of re-explaining to AI tools.

Leave blank what you do not know; a blank becomes a marked blank, never a guess. The build runs no git or gh command, so the repo hubs come out with blanks such as `_left blank, needs gh_`, filled in by your first request afterwards.

## What you get

- `Repos/<repo-name>/<repo-name>.md`: one hub per repository, named exactly like the repository on GitHub, so `example-org/checkout-api` becomes `Repos/checkout-api/checkout-api.md`. It is the one place in the vault where lowercase and hyphens are allowed. Its sections: Current state with a date; Repository (local path, GitHub URL, default branch, and the commit the hub was read at); Serves (the projects it serves, with a link to the project hub where the deploy order lives); Architecture, ten lines stamped with that commit; Documents to read, paths rather than copies; Run and test; Conventions; Gotchas; Live views, the exact `gh` commands for your open pull requests with their checks, the ones awaiting your review, and failing workflow runs, each with `-R <owner>/<repo>` so that no command depends on the folder it runs in; Notes in this folder. The results of the Live views are never stored. Nothing is mirrored from the repository by default; the hub points at documents instead of copying them.
- `Projects/<Name>/<Name>.md`: the goal, Current state with a date, the repositories it touches with the part each serves, the branch, the pull request, and the deploy order, the tracker and its named queries, Milestones, Next steps with owners, Waiting on, Risks, Open questions, and links to its decisions.
- One running log per project, `YYYY-MM-DD <Name> Log.md`, newest entry at the bottom, in the same shape every time: `## YYYY-MM-DD`, then What happened, Decided, Next, Waiting on, Links (commits, pull requests, issues, tracker items by URL), Source. One entry per day; a second session on the same day extends that day's entry under its headings. A repository gets a log of its own on first need, for work that belongs to no project.
- Decision notes, dated, `type: decision`: Context, Decision, Alternatives, Consequences, Decided by and when, Status. The alternatives are kept so the reasons survive the people. A decision that belongs in a repository goes there through a pull request, and the hub links it by URL.
- Design notes, `type: plan`, before non-trivial code, and incident notes, tagged `incident`, in the repository's folder.

The AI keeps the parts of a repo hub that describe the repository as it is, without asking, and reports what it changed. Gotchas it proposes. Decisions, design notes, and anything you wrote it changes only after showing the before and after and getting your yes.

## How projects map to repositories

A project spans repositories. Its hub lists each one with the part it serves, the branch the work is on, the pull request, and the deploy order: infra first, then the service, then the web client, for example. That standing order lives in the project hub; a design note records the merge order for the one change it describes. A repository shared by several projects has one hub, linked from every project that uses it. Ticket-sized work is a log entry, not a project. A standing responsibility, such as owning a service, is a project whose Goal says ongoing. Session entries go in the project log. A repo log is created on first need and holds only work that has no project.

## Teach the AI your repositories

- "Read my repos and fill in their hubs": the first request after the build. For each repository in your profile, the AI reads the README, the structure, the build files, and the entry points, fills in the hub, and records the commit it read.
- "Add the repo at [path]": a new folder and hub under `Repos/`, which is created on first use if the module was off.
- "Refresh the hub for [repo]": when the commit moved or 30 days passed. Before relying on a hub, the AI checks the current commit; if it moved, or the hub is older than 30 days, it re-reads the repository first and says so. When the repository contradicts a note, it updates the AI-maintained part and leaves your words alone.
- "Scaffold a new service like checkout-api, at [path], for [purpose]": the payoff of a good hub. The AI proposes the layout from the hub's Architecture, Conventions, and Key files, and a design note comes first, before any file is written.

Infrastructure code, a shared library, or a module repository follows the same pattern: a repo hub for the repository the pieces come from, a design note before any code, pinned versions and no secrets in the project's repository, and a decision note and a log entry to close the loop.

## A coding session

1. Open the AI tool on the vault and say "Start on [project]" or "Where did we leave off on [repo]?". The AI reads the hub and the last three log entries. In each repository the hub names, it checks the working tree, the current branch, the last ten commits, and the open pull requests with their checks. It reads the linked tracker item, refreshes the hub's Current state, and answers in ten lines: where you left off and when, what moved since, what is next, what is waiting. For a story that has a spec in the repository, say "Start on ALPHA-123" instead; what it reads and the plan it prints are under "A story with a spec" below.
2. Work. Before non-trivial code the AI writes a design note: Problem, Constraints, Options considered, Chosen approach, Repos touched and merge order, Rollout and rollback, Open questions, Status. It waits for your yes before touching a repository. Then it works on a branch, never on the default branch, shows the diff and the message before a commit and the title and body before a pull request, checks for secrets before every commit, and never force-pushes, rewrites shared history, deletes branches, or changes repository settings.
3. "Draft the PR for this branch": the AI reads the diff against the default branch, the log entries, the ticket, and the repository's pull request template, shows the title and body, opens the pull request after your yes, and records the URL. When the branch or its commits carry a story key, the body also gets an Acceptance criteria section, one line per criterion id, met or not met, as described under "A story with a spec".
4. "Close the session": the AI drafts the log entry from the commits since the session started and your open pull requests in the repositories named in the session or in the project hub, appends it to the project log, or to the repo log for work with no project, updates Current state and Next steps, proposes new Gotchas for the repo hub, adds one `AI:` pointer line to today's Log, and reports what changed.

An incident gets its own dated note in the repository's folder, tagged `incident`, with the pull requests, workflow runs, and tracker items linked by URL. The hub links the note, and what the incident taught goes into Gotchas.

On your reporting day, "Close the week" runs "What did I ship this week?": merged pull requests by repository, closed tickets, and the week's log entries. When your lead wants a status in the five standard headings, ask for a status report on the project; the headings and the sourcing rules are in [prompts/weekly-status-report.md](../prompts/weekly-status-report.md).

## A story with a spec

When a product owner writes a spec per story, it lands in the repository as `specs/ALPHA-123.md`, named after the tracker key, through the product owner's pull request, or on the story as a comment until your first commit adds the file. It holds Story, Why, Scope with In and Out, Acceptance criteria AC1 and up as Given, When, Then with a Verify line each, Data and interfaces with sample values only, Where in the code as a proposal read at a named commit, Non-functional needs, Rollout, Open questions with owners, Sources, and Revisions. The repository's rulebook carries a Specs block that tells every tool to read that file first. What changes for you:

- "Start on ALPHA-123", the key form of "Start on [project]", works in the repository with or without the vault. The AI reads `specs/ALPHA-123.md` first, with `git fetch origin` and `git show origin/main:specs/ALPHA-123.md` (`main` is the default branch the hub records), and never switches your clone to another branch. Without the file, it reads the story's comments for a spec and offers to add it as `specs/ALPHA-123.md` on the branch, or asks for one before planning. Then it reads the story (key, title, state, owner, dates, and the comments newer than the spec's version line), the project and repo hubs and the last three log entries when the vault is present, and the checks of step 1: `git status --short`, `git branch --show-current`, `git log --oneline -10`, `gh pr status`. If the default branch moved past the commit stamped in Where in the code, it re-reads those paths and names the ones that moved. The ten lines are the answer; the plan follows, one line per criterion. It waits for your yes before it creates the branch `alpha-123-retry-on-timeout` (the key in lowercase and the short title with hyphens), or the team's shape when the repository's rulebook names one, with `git switch -c alpha-123-retry-on-timeout origin/main`. A name that matches a hub exactly is a project; otherwise a word shaped like a key whose prefix matches a tracker project key recorded in one of your hubs is a story, and "Start on ALPHA-123 in checkout-api" says which repository when more than one could apply, or when the prefix maps to none.
- The plan stands in for the design note when the work stays in one repository and needs no migration: one line per criterion with the files and the test that will be its proof, Out named, blocked criteria named with their question. A design note is still written when the work spans repositories, needs a migration, or diverges from the spec's Where in the code. It then links the spec by URL and covers Options considered, Chosen approach, merge order, and Rollout and rollback, because Problem and Constraints are the spec's Why and Scope.
- Questions go through the story, never through a guess. For each gap the AI shows the comment with the opener "Spec question, AC3:", as `acli jira workitem comment create --key "ALPHA-123" --body "Spec question, AC3: ..."` (check your version for `create`), `jira issue comment add ALPHA-123 "Spec question, AC3: ..."`, `gh issue comment 123 -R example-org/checkout-api --body "..."`, or `az boards work-item update --id 123 --discussion "..."`, and sends it on your yes through the tracker tool the spec's Story line names. The criterion is skipped, and the plan and the pull request say so. The answer arrives as "Spec answer, AC3:" with a revised spec, which the next "Start on ALPHA-123" reads. With the vault, the question lands under Waiting on in the project hub with the product owner's name and the date. Never change a spec file in a code pull request. The one exception is the read-access route: the file is added verbatim from the product owner's story comment, in its own commit, and a newer `Spec ALPHA-123, r2` comment replaces it the same way; it is still never edited. A criterion you need changed is a question, and a correction to Where in the code goes in the pull request body.
- "Draft the PR for this branch" keeps its sources: the diff, the log entries, the ticket, the pull request template. When the branch or the commits carry a story key, it reads the spec too and gives the body an Acceptance criteria section, one line per id in the spec's order: `AC1 met: tests/payments/test_retry.py::test_alpha_123_ac1_retries_once, unit, run <URL>`; `AC2 removed in r2`, and nothing else, for a criterion the product owner dropped; `AC3 met: manual, steps below, on staging 2026-11-13`; `AC4 not met: blocked by Q1, asked on ALPHA-123 on 2026-11-11`; then `Differed from Where in the code: ...` when a path was wrong. A test that proves a criterion carries the key and the id in its name, in the language's own naming, such as `test_alpha_123_ac1_retries_once` or `TestAlpha123AC1RetriesOnce`, so a search for the key and the id finds the proof, and a tester reads the spec's Verify line next to the pull request's line for the same id. `gh pr create` runs after your yes, and the URL goes in the vault log when the vault is present. A tester reports a failing criterion as a story comment, "AC4 fails: ...".
- "Close the session" works as today. The log entry links the story, the spec file at its version, and the pull request by URL. The story transition the team uses (`acli jira workitem transition --key "ALPHA-123" --status "In Review"`, or the tracker's equivalent from the Tracker Commands note) is offered as a command and never run on its own. A wrong Where in the code becomes a Gotcha for the repo hub, and the next spec is drafted from the hub. The product owner's "Close the week" reads the criteria lines of your merged pull request; nobody edits the vault note for it.
- "Review the spec for ALPHA-123" works from the repository too. The findings print against `origin/main:specs/ALPHA-123.md` after `git fetch origin`, or the open spec pull request, and a review comment is shown as `gh pr review <number> -R example-org/checkout-api --comment --body "..."` for your yes. The AI never approves a spec on anyone's behalf.
- The GitHub Copilot cloud agent (renamed from the Copilot coding agent) picks up a GitHub issue assigned to Copilot in the browser (Assignees, Copilot) and always opens a pull request. It reads the repository's `AGENTS.md` (the nearest one wins), a root `CLAUDE.md`, and `.github/copilot-instructions.md` on its own, so the team's Specs block is what makes it read the spec first, plan per criterion, and write the criteria lines in its pull request. It cannot wait for a yes, so it puts the plan at the top of its pull request body, and its pull request is reviewed like any other, since it works from issue text. It receives the issue's title, description, and existing comments at assignment and sees no later comment, and it is not documented to follow links, so the issue body names the spec's repository path, and the file must be on the default branch before the hand-off. For a Jira or Azure DevOps story, you create that issue, shown first: `gh issue create -R example-org/checkout-api --title "ALPHA-123: Retry on timeout" --body "Spec: specs/ALPHA-123.md. Story: https://example.atlassian.net/browse/ALPHA-123. Follow the Specs section of AGENTS.md."`, and comment the issue URL on the story. The agent's questions land in its pull request under the criterion, and the developer who reviews the pull request carries them to the story as "Spec question, AC3:". From a terminal, `gh agent-task create -R example-org/checkout-api -F task.md` starts the same agent (a preview command; check your version); assigning an existing issue to Copilot is done in the browser, or through the API with `gh api` as GitHub's cloud-agent API page shows.
- Without a vault, everything above works from the repository's rulebook and the tracker tool the spec's Story line names, because the spec, the key, and the comment openers live in the repository and the tracker. The vault adds the hub, the log, "Where did we leave off on checkout-api?", and the Waiting on line for an open question.

## Your own notes

- Today's note, `Daily/YYYY-MM-DD.md`, has two sections, Plan and Log. "Start my day" creates it and adds up to ten `AI:` lines under Plan, each with its source: unchecked items from yesterday, Next steps and Waiting on from your hubs, your open pull requests and the ones waiting for your review, and the items assigned to you in your trackers. "Start my day, vault only" skips the tracker reads. Every line the AI writes starts with `AI:`. It never edits, reorders, or ticks a line of yours.
- "Add to today: [line]" appends your words to the Log as they are. Type into the Log all day: what you did, a gotcha, a decision, an idea, a to-do.
- "Close my day" shows a filing table for the day's Log lines, and one yes applies it: a gotcha goes to the repo hub, a decided line becomes a decision note, an idea with a title becomes a note in `Notes/`, a line that belongs in a tracker is shown as a command, and the rest stays. It also offers to close any session not closed today.
- `Notes/` holds ideas and learning notes, tagged `idea` or `learning`. `Library/` holds what others could reuse: how-tos, snippets, checklists, standards. A learning note moves to `Library/` once it is reusable.
- "Write this week's review" writes `Notes/YYYY-MM-DD Weekly Review.md` from the week's daily notes, logs, and shipped list: What moved, What stalled, Promises kept and not kept, What to drop, Next week's three.

The capture table, with where each kind of line goes, is in [docs/04-working-day-to-day.md](../docs/04-working-day-to-day.md).

## Which tool

- Claude Code (in the terminal, or the Code tab of the Claude desktop app), Codex, GitHub Copilot CLI, and GitHub Copilot in VS Code with the vault as the workspace can open the vault folder and read its rulebook. Setup and the check for each are in [docs/02-connect-ai-tools.md](../docs/02-connect-ai-tools.md).
- A session you start inside a repository does not read the vault's rulebook on its own. [Connect your AI tools](../docs/02-connect-ai-tools.md) has the two routes: start in the vault and add the repository with `--add-dir`, which Claude Code, Codex, and Copilot CLI all have; or start in the repository with the one-line pointer the build prints for `~/.claude/CLAUDE.md` or `~/.codex/AGENTS.md`, copied by hand into `~/.copilot/copilot-instructions.md` for Copilot CLI, and add the vault with `--add-dir` when you need to write there. Copilot in VS Code reads the `AGENTS.md` at the workspace root, so open the vault as the workspace for vault work and attach the hub files for code work. Check once with "Read AGENTS.md and tell me the reading order".
- Claude chat, ChatGPT in the browser, and Microsoft 365 Copilot cannot open the folder. "Context pack for [hub]" prints one block to paste as the first message in Claude chat or ChatGPT: how you work with AI, Current focus, the hub, the last three log entries, each linked repo hub's Run and test, Conventions, Gotchas, and Architecture, and the Live views run now. Whatever comes back, you paste to the vault tool with "from [tool], [date]" as its source. Microsoft 365 Copilot is where a pasted status lands, in Outlook, Teams, Word, or Loop; it does not read the vault.
- When a repository carries its own `AGENTS.md` or `CLAUDE.md`, that file governs the code. The vault's rulebook governs anything written in the vault.
- With a spec in the repository: in VS Code with the repository as the workspace, the Specs block of its `AGENTS.md` loads on its own; on github.com, open Copilot Chat with "Read AGENTS.md and specs/ALPHA-123.md first"; in ChatGPT or Claude chat, paste the spec file as the second message after a context pack. It is plain Markdown with no properties block, so the ids survive the paste. The ChatGPT desktop app opened on the repository in its Codex mode is Codex: the Specs block loads on its own. Microsoft 365 Copilot reads no repository and runs no command, so it has no part in building a story; it is where the spec's paste-ready copy goes for stakeholders.

## Trackers

Each project hub records its tracker, the command-line tool, and its named queries. The exact commands live in `Library/YYYY-MM-DD Tracker Commands.md`; `AGENTS.md` holds only the rules. Read commands run freely. Write commands, such as creating, assigning, or transitioning an item, are shown first and run after your yes. Items are linked by URL, and the AI copies only the key, title, state, owner, and dates. When you ask for status, it reads the tracker first and the vault second, and says which is newer when they disagree. A tool that is not signed in gets one line saying so, and the AI continues from the vault.

- `gh` for GitHub repositories, pull requests, issues, and workflow runs, each command with `-R <owner>/<repo>` from the hub.
- `gh project` for a GitHub Projects board. It needs the `project` scope on your login, added once:

```
gh auth refresh -s project  # add the project scope to an existing gh login
gh project item-list <number> --owner <org> --query "assignee:@me -status:Done"  # your open items on a board; needs gh 2.87.0 or newer
```

- `acli` or `jira` for Jira. `az boards` for Azure DevOps work items. Code is on GitHub, so nothing from Azure Repos is needed.

Sign-in and the full command list per tracker are in [docs/03-connect-work-trackers.md](../docs/03-connect-work-trackers.md).
