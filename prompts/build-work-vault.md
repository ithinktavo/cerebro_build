# Build prompt: a work vault the AI designs for you

This prompt turns an empty Obsidian vault into your work notebook and the context your AI tools read first. You fill in a short profile, the AI proposes a design for your roles and tools, you say yes, and it builds the whole vault in one pass: the rulebook, your home note, hubs for the real things you own, templates, and the two daily rituals.

## How to use this file

1. Create an empty vault in Obsidian and turn on the Daily notes and Templates core plugins. See [Set up Obsidian](../docs/01-set-up-obsidian.md).
2. Open a tool that can read and write the folder on that vault: Claude Code (in the terminal, or the Code tab of the Claude desktop app), Codex, or GitHub Copilot (the CLI, or VS Code with the vault as the workspace). See [Connect your AI tools](../docs/02-connect-ai-tools.md). Claude chat, ChatGPT in the browser, and Microsoft 365 Copilot cannot create files; the ChatGPT desktop app in its Codex mode counts as Codex.
3. Fill in the profile between the square brackets. Leave blank what you do not know. A blank becomes a marked blank in the vault and a question for later, never a guess. If you use a tracker, also paste the Read and Write blocks for it from [Connect your work trackers](../docs/03-connect-work-trackers.md) under the profile, so that the Tracker Commands note copies the command shapes and marks only versions.
4. Keep `Design first`, the default, to read a short design and answer up to five questions before anything is written. Choose `Build now` to skip the design and build with the defaults.
5. Paste everything below the line as your first message. Expect a design to read, then about twenty-five files, then the settings to set in Obsidian. In a mode that asks before each write, expect one approval per file. If the build stops partway, say "Continue the build: compare the tree to the approved design and re-run the verification"; the stop on a non-empty folder is where a resumed build starts, not an error.

---

Build my work vault. This folder is a new, empty Obsidian vault. Read my profile, design the vault for it, and build it as described below. Make sensible choices, cite my profile for every fact you write, and list every assumption at the end.

Before anything else: if the folder holds anything besides the `.obsidian` folder, stop and show me what is in it, and offer to extend what is there by proposing additions only. Take today's date from the system clock (`date +%F` on Mac or Linux, `Get-Date -Format yyyy-MM-dd` on Windows). During the design and the build, run no tracker, git, or gh command and read nothing outside this folder.

## What the vault is for

1. My notebook. One daily note is where everything lands during the day. Ideas, things I learn, and how-tos for myself have a home. Notes I write by hand are mine; you treat them as information and change them only with my yes.
2. The context every AI tool reads first: who I am, what is current, what each project, team, and repository is, what was decided and why, and where we left off.
3. Capture in one place, filing done for me: I type lines, you propose where each one goes, and one yes applies the batch.
4. Reports from sources, not memory: team status, roll-ups, and reviews, every line with its source.
5. GitHub and the work trackers stay the systems of record. The vault links to them and never copies them, and you read them through their command-line tools when I ask.

## The spine every vault has

```
AGENTS.md          the single rulebook, read by Codex and GitHub Copilot on their own; under 200 lines and 32 KiB
CLAUDE.md          pointer for Claude Code: one sentence and four @ lines; no rules
Me.md              who I am, what I own, my week, my note habits, how I work with AI; mine to edit
Home.md            front door: current focus, what to say, one line per hub, trackers and tools, library
Daily/             one note per work day, YYYY-MM-DD.md, from the core Daily notes plugin; no properties
Notes/             anything with a title and no hub: ideas, learning notes, weekly reviews, one-off meeting notes
Library/           reusable knowledge with no single owner: how-tos, checklists, standards, reusable prompts
Projects/          one folder per thing with a finish line, with a hub named like the folder and one running log
System/
  Templates/       one template per kind of note this vault uses
  Attachments/     images and exported deliverables, dated names, linked from a hub
  AI/              AI-Memory.md and AI-Log.md, your working notes
Archive/           created later, with my yes, when the first project finishes
```

## The modules and the rule for each

- **Developer**, when I name a repository or my roles include developer, tech lead, or architect: `Repos/<repo-name>/` with a hub named exactly like the repository on GitHub, the one place lowercase and hyphens are allowed; a running log on first need; incident notes.
- **Teams**, when I name a team or someone reports to me: `Teams/<Team>/` with a hub, a running check-in log created with it, status reports, decisions, and, only if I said yes above, one running one-on-one log per direct report. A direct report who covers several teams gets the log in the first of those team folders, linked from the others.
- **Reports**, when I owe a recurring report across more than one team or project, or my roles include manager, PM, or director and I named a report: `Reports/` with a hub of recipes and open asks, weekly roll-ups, and monthly reviews.
- **Specs**, a switch rather than a module, when Specs for my stories says yes: no folder. It adds the Spec template, a Specs section in each project hub and in each repo hub my stories land in, the four spec phrases below, and two morning lines per project. The repositories my stories land in go on the Repositories line and switch Developer on as above, read only or not.

Nothing is built in case. A module I did not trigger is created on first use under the normal rules: "Add the repo at [path]" creates `Repos/`. A team named only as the one that builds a project does not switch Teams on; the Teams line does. No other folder kinds exist: no People, Areas, or custom folders. A folder for something new is proposed later, when three notes on one topic pile up in `Notes/`. Someone who is both a developer and a manager gets one vault with all three modules, one daily note, and one set of rituals.

## Design rules

- A hub is named exactly like its folder, states Current state with a date, and links every note in its folder. A project or team hub is created together with its running log; a repo hub gets its log on first need; the Reports hub has none.
- Real names from my profile, with marked blanks such as `_left blank, needs gh_` where you would need a tool. No example folders.
- A standing responsibility is a project whose Goal says ongoing. Ticket-sized work is a log entry, not a project; with Specs on, a story I specify also gets one spec note in the folder of its project, and still no project.
- A fact lives in one note. Hubs and `Home.md` quote it with a date and a link.
- Names and roles only for other people. Nothing about performance, pay, health, or personal matters. No secrets, no customer data.

## Hubs

Sections, in this order. Every hub opens with Current state (as of a date, AI-maintained, one line per fact with its source) and ends with Notes in this folder.

- Project hub: Goal; People (owner and stakeholders, name and role only); Teams (one line per team with what it owns); Repos (one line per repo with the part it serves, the branch, the pull request, and the deploy order, which is where that standing fact lives); Tracker and queries (with the project key); Specs (with Specs on: one line per story, newest first: key and title by URL, state as of a date, the note by link, the repository file or the story comment by URL); Priorities; Milestones (date, what, status, source); Next steps (checkboxes with owner); Waiting on (who, what, since when); Risks (risk, owner, raised, status, mitigation); Open questions; Decisions (one line each, linking the note); Log (link to the running log).
- Repo hub: Repository (local path, GitHub URL, default branch, read at commit); Serves (the projects, with a link to where the deploy order lives); Architecture (ten lines at most, stamped with the commit); Documents to read (paths, never copies); Run and test; Conventions; Specs (with Specs on: the folder, the file rule, the key prefix (none for Jira; GH- for a GitHub issue; AB- for an Azure DevOps work item), the PR template path, the test layout, whether the rulebook names specs, the reviewer, my access, who can read story comments, each stamped with the command and date); Gotchas (dated, each with a source); Live views (the exact `gh` commands; results never stored).
- Team hub: Team (reports through; members by name and role); Works on; Cadence; Tracker and queries; Priorities; Milestones; Next steps; Waiting on; Risks; Open questions; Decisions; Reports (the recipe line, then the reports, newest first). The check-in log and any one-on-one logs are listed under Notes in this folder.
- Reports hub: Recipes (one per recurring report: audience, cadence and day, headings, sources, destination, link to the last one); Open asks of leadership (what, who decides, since when; refreshed on every roll-up).
- `Home.md`: see Files to write.

## The design pass

In `Design first` mode, print the design in chat, under 80 lines, and write nothing until I say yes:

1. Modules on and off, and the Specs switch, one reason each.
2. A mapping table, one row per thing I own: item, module, links (which repos serve which project, which team works which initiative, which tracker holds what).
3. The tree with my real names and one line of reason per folder.
4. The hub sections you will keep, the Specs sections if the switch is on, the templates, and the daily note's two sections, with what the morning will pull for my roles.
5. The report recipes with their cadence, if any.
6. The rituals, with the exact words, in my names.
7. The local repository paths you will read only when later asked, the first five requests, and your assumptions.
8. At most five questions, each with the default a bare yes takes, or none, with one line saying why. Ask only when the answer changes the structure and my profile left it open: is X a team, a project, or a repo; which tracker is the record when two are named; 1:1 logs or not; specs for my stories or not, when my roles include product owner and the line is blank; flat teams or grouped by manager when more than about twelve are named; whether leadership reads by team or by initiative. Never ask for URLs, ids, tokens, anything already in my profile, or permission for your own bookkeeping.

End with: "Reply yes to build with these defaults, or tell me what to change." Rounds continue until I say yes. In `Build now` mode, skip the pass, take every default, build, print the same summary afterwards, and put the unasked questions in `AI-Memory.md`.

## The daily note and the two daily rituals

The daily note is `Daily/YYYY-MM-DD.md`, with two sections: `## Plan`, checkboxes for today, and `## Log`, one line per thing as it happens, in my words. No properties. Starting a Log line with `[[Hub]]` is an optional hint about where it belongs; you use it when present and infer the home from the words when absent.

Ownership, written into `AGENTS.md`: you never edit, reorder, or tick a line I wrote; every line of yours starts with `AI:`; "Add to today: [line]" appends my words verbatim; the only change you ever make to my line is the filing marker ` → [[Hub]]` appended after my yes; you re-read the note right before every write.

**"Start my day"**: take the date from the clock, search the vault for today's note, and create it from the template if none exists. If any daily note since the last `AI: closed` marker has unfiled Log lines, run "Catch me up" first. Read yesterday's unchecked Plan items (carry them with the date first seen; on the third morning, flag it: give it a date in a hub or drop it), every hub's Next steps owned by me and Waiting on older than seven days, my week and each team's cadence for today's commitments and what inputs a report due this week still lacks, teams with no check-in this week, hubs whose Current state is past 30 days, and the open questions in `AI-Memory.md`. Then the trackers: my open pull requests and the ones waiting for my review, items assigned to me through each tracker's assigned-to-me query, and each team's blocked query. With Specs on, per project: stories next up with no spec, from the project's recorded next-up query matched against `git ls-tree --name-only origin/<default branch> -- specs/` after a fetch and the spec notes in the vault, and developer questions on delivered stories, from the project's recorded spec-question query, keeping only comments whose first words are "Spec question" and that are newer than the spec's version line, answered ones dropped against the note's Revisions; until a query is recorded the line says so, and the changed-in-7-days query gives a candidate list named as such; a cadence with no next date recorded gets one line saying so, and the missing date goes to `AI-Memory.md`. A tool that is not signed in or that fails gets one `AI:` line saying so, and the ritual continues from the vault; "Start my day, vault only" skips the reads. Append at most ten `AI:` lines under Plan as plain bullets, never checkboxes, each ending with its source. Never read a calendar or an inbox.

**"Close my day"**: re-read today's note; take the Log lines after the last `AI: closed` marker; show a filing table, one row per line: the line, its destination, the action. A check-in line becomes a dated entry in that team's log plus the hub edits it implies; a promise or a waiting-on line goes under Next steps or Waiting on in the right hub with owner and date; a decided line becomes a dated decision note; a gotcha goes to the repo hub; an idea with a title becomes a note in `Notes/`; a line that belongs in a tracker is shown as a command on its own; a line that stays is marked stays; a line you cannot place is asked about. One yes applies the batch, the marker is appended to each filed line, and `AI: closed HH:MM` ends the section; with nothing to file and no line of mine to mark, the closed marker is appended without asking. Offer to close any session not closed today. List what I promised and to whom. Unchecked Plan items stay. Update `AI-Memory.md` and `AI-Log.md`, and print a three-line summary. "Catch me up" runs the same table over every unclosed daily note since the last marker. "Undo the last batch" reads the lines of the last Close my day in `AI-Log.md` and shows the reverts, file by file, for one yes.

## Logs, sessions, decisions, meetings, designs

- Every project, team, and repo has one running log, `YYYY-MM-DD <Name> Log.md`, created with the hub (a repo log on first need), newest entry at the bottom. A team's running log is its check-in log. One entry shape for all: `## YYYY-MM-DD`, then What happened, Decided, Next, Waiting on, Links (commits, pull requests, issues, tracker items by URL), Source. One entry per day; a second session on the same day extends that day's entry under its headings. A repo log is created by the first "Close the session" or log entry about the repository, not by filling the hub.
- "Start on [project]", "Start on [KEY]" for a story, or "Where did we leave off on [repo]?": read the hub and the last three log entries; in each repo the hub names, run `git status --short`, `git branch --show-current`, `git log --oneline -10`, and `gh pr status`, which shows each pull request with its checks; read the linked tracker item; refresh the hub's Current state; answer in ten lines: where we left off and when, what moved since, what is next, what is waiting. A name that matches a hub exactly is a project; otherwise a word shaped like a key whose prefix matches a tracker project key recorded in a hub is a story, and "Start on [KEY] in [repo]" says which repository when both could apply. For a story key, in the clone, run `git fetch origin` and read `specs/<KEY>.md` with `git show origin/<default branch>:specs/<KEY>.md`, never switching branches; then the story and the comments newer than the spec's version line; if the default branch moved, refresh the repo hub's Read at commit and Specs folder lines, and if it moved past the commit the spec names, re-read the paths it names; a spec that reached the default branch without a known pull request is recorded as merged at [sha], reviewer unknown; the ten lines are the answer; then the plan, one line per criterion with the files and the test that will prove it, blocked criteria named, Out named, and the branch proposed from `origin/<default branch>` as `[key in lowercase]-[short title in lowercase with hyphens]`, such as `alpha-123-retry-on-timeout`, or the team's shape when the repository's rulebook names one; then wait for my yes.
- "Close the session": draft the log entry from `git log` since the session started and `gh pr list --author @me` in the repos named in the session or in the project hub, never every recorded path; append it to the project log or, for work with no project, the repo log; update Current state and Next steps; propose new Gotchas for the repo hub; append one `AI:` pointer line to today's Log; report. For a story, offer the transition the team uses, command shown.
- "Log this check-in for [team]: [lines]": a dated entry in the team's check-in log in my words with its source ("said in chat", or the recap or update I pasted, with the date); the hub edits it implies, shown for one yes; a tracker item offered where a line deserves one, command shown; what I promised, listed.
- "Write a decision note: we decided X because Y; the alternatives were Z": a dated `type: decision` note with Context, Decision, Alternatives, Consequences, Decided by and when, Status (proposed, decided, reversed), linked from its hub. A decision that belongs in a repository goes there through a pull request, and the hub links it by URL.
- "Turn these notes into a meeting note for [hub]: [paste]": attendees by name and role, context, discussion in my words, decisions each linking their note, actions with owner and date, and the source with its date (my notes, a transcript, a Teams recap). A meeting with no project or team goes to `Notes/`. Actions that belong in a tracker are offered with the command shown.
- A design note, `type: plan`, comes before non-trivial code: Problem, Constraints, Options considered, Chosen approach, Repos touched and merge order or Teams and milestones, Rollout and rollback, Open questions, Status. You wait for my yes before touching a repository. A story with a spec in its repository needs a design note only when the work spans more than one repository, needs a migration, or diverges from the spec's Where in the code; otherwise the plan from "Start on [KEY]" stands in and still waits for my yes.
- "Draft the PR for this branch": the diff against the default branch, the log entries, the ticket, and the repository's PR template; title and body shown; `gh pr create` after my yes; the URL recorded. When the branch or its commits carry a story key, read `specs/<KEY>.md` too, and give the body an Acceptance criteria section, one line per id: met, with the test or check that proves it and a link, or not met, with the reason or the question; say where the code differed from the spec's Where in the code; the code pull request never edits the spec file.
- "Prepare my 1:1 with [name]", only if 1:1 logs are on: their log, the team hub's Waiting on and Risks, their tracker items this week. Work topics only.
- "What is waiting on me?": review requests and comments on my pull requests, and Waiting on in every hub where I am the one who owes, each with who and since when. "What am I waiting on, and since when?": Waiting on in every hub, oldest first. "What do my notes say about [topic]?" and "When and why did we decide [X]?": an answer from the vault with links to the notes, and "not in the vault" rather than a guess.

## Specs for my stories, written into AGENTS.md when the switch is on

A spec is one note per story I write, `YYYY-MM-DD <KEY> <Short Title> Spec.md`, `type: plan`, tag `spec`, from the Spec template, in the folder of the project the story serves, or of the repository it lands in when it serves none, or `Notes/` with the tag `spec` when there is neither, where three such notes make you propose a project, listed under Specs in that hub when it has one. It opens with `# <KEY>: <title>` and keeps these headings in this order, none dropped and `none` allowed: Story (the story by URL with its state as of a date and the tool it is read with, the epic by URL, the repository, the reviewer by name and role, and the version line `r1, [date]`, `r0` while a draft, bumped on each revision); Why; Scope (`In:` and `Out:`, two labelled list lines); Acceptance criteria; Data and interfaces, opening with "Sample values only" and marking a path or name the story creates as new; Where in the code, whose heading reads exactly `## Where in the code (AI proposal, read at commit [sha] on [date])`; Non-functional needs; Rollout; Open questions (Q1, Q2, each with the owner, who is the one who answers it, the date asked, and the criterion it blocks or "blocks nothing"; an answered question keeps its line and id and gains `Answered [date]: [answer]`, and its Blocked by lines are removed); Sources; Revisions. The key is written as the tracker prints it and matched without regard to case; a GitHub issue is GH-123 and an Azure DevOps work item AB-123, with the prefix recorded in the repo hub's Specs section. Under 80 lines as `wc -l` counts the repository file, blank lines included, not counting the lines under Revisions; the note's properties block and its Delivered and Built by lines do not count either; Why three lines at most; Where in the code five at most; the short title two to four Title Case words. Each criterion is a block, `### AC1` plus at most four words, then Given, When, Then with one observable result and exact values, and Verify naming the test path, the manual steps, or the metric and its threshold, proposed from the repository's test layout; three to seven; ids never renumber, a dropped one stays as `AC3 removed in r2` with no lines under it, printed as that in the plan and the pull request and skipped by the review, and `- Blocked by: Q1` ends a criterion a question blocks. A line I did not state and you did not read from the story or the repository starts with `AI:` until my yes confirms or drops it; my reply names the proposals to keep, the prefix comes off those, and the rest are removed or moved under Open questions; a line read from the repository ends with its path and commit; what I said, in the story or in chat, carries no marker and is listed under Sources as "[my name] in chat, [date]". A story whose spec needs more is two stories: say so instead of writing a longer spec.

- "Spec for [KEY]", or "Spec for [KEY]: [what it must do]": read the story in full through its tracker tool, the project hub and its Decisions, the repo hub, and the clone at its current commit (in a clone my profile marks read only, after a fast-forward; in any other clone, from `origin/[default branch]` with `git show` and `git ls-tree` after a fetch); a project key the hub lacks is recorded in its Tracker and queries section and in `Home.md`, and you say so; replace a customer, an account, a record, a log line, a production value, an internal hostname, an IP address, or a request, session, or trace id with a placeholder and name it in your reply; read an image, a screenshot, or a pasted export for field names and shapes only, never saving or linking it; show the whole draft with its path and the hub line; create it after my yes, with the project hub's Specs line, the open questions under the hub's Open questions with owner and date, and a log entry; when my yes arrives together with answers to open questions, apply them to Open questions (`Answered [date]: [answer]`, Blocked by lines removed) and to Sources, show any other line an answer changes as before and after, and create the note only with that. Nothing is written to the repository or the tracker.
- "Review the spec for [KEY]": re-read the note, or the repository file once delivered, and print a table, pass or fail per check: every Then names one observable result with an exact value; every criterion has a Verify line naming a test path, manual steps, or a metric and its threshold; every criterion heading is AC plus at most four words; Out has at least one line; every path exists at the current commit, or the line marks it new; every open question has an owner and a date, and a blocked criterion says so; no `AI:` line remains outside Where in the code; nothing looks like customer data, a record, a secret, a hostname, or an id; three to seven criteria and under 80 lines; the story link resolves and its title matches. A check that cannot run prints `not checked` with the reason; with no tracker tool the title must match the pasted story; `not checked` does not decline a delivery, a fail does. Fixes are shown as before and after for one yes, or through "Revise" once delivered.
- "Deliver the spec for [KEY]": run the review; a fail declines, `not checked` does not. Access: `gh repo view <owner>/<repo> --json viewerPermission`, or, if that fails, what my profile or the repo hub records, confirmed by me in chat, or ask. Stop unless `git status --short` prints nothing; `git ls-files`, matched without regard to case, lacks the path (a spec already in the repository changes through "Revise"); and `git branch --list spec/<KEY>` and `git ls-remote --heads origin spec/<KEY>` print nothing, or that branch holds this spec's commit and you switch to it and resume from the push. With write access, one set: fast-forward, branch `spec/<KEY>`, the note's body without its properties as `specs/<KEY>.md` or in the folder the repo hub records, its version line bumped from `r0` to `r1, [date]` and its Revisions section set from `none` to `r1, [date]: delivered for review`, commit `<KEY>: add spec`, push, `gh pr create` titled `Spec <KEY>: <title>` with the reviewer, or without `--reviewer` when the repo hub records no handle, the body naming the reviewer and the set saying so (the handle is added later with "My reviewer's handle for [repo] is [handle]; update its hub"), then, after reading who can read story comments from the repo hub's Specs section, asking when that line is blank, and saying who can read the story, the comment `Spec r1 for review: [pull request URL]. After the merge: specs/<KEY>.md on <default branch>. Questions here as comments that open with the criterion id, as the Specs section of AGENTS.md says.`, ending after "the criterion id" while the repo hub says the rulebook does not name specs, internal where the tool has the option, and the switch back. One yes covers the set, the tool's prompts still ask, nothing runs before it; the reviewer or the team merges, never you. If the push fails, stop: the clone is on `spec/<KEY>` with the commit, and "Deliver" again resumes from the push; never delete the branch, and never reset, restore, clean, stash, or force-delete a branch. If `gh pr create` fails, keep going: record the exact command under Waiting on tools in `AI-Memory.md`, post or print the story comment with the branch and the file path in place of the URL, switch back, and write `Delivered [date]: branch spec/<KEY> at [sha], pull request pending, specs/<KEY>.md. The repository file is what developers follow.`; when the pull request is created later, or the file reaches the default branch without one, rewrite the Delivered line and the note's Revisions lines to the URL or to `merged at [sha], no pull request`, and post nothing twice; while no pull request exists, one pull request for the branch later covers every revision and keeps the r1 title.
