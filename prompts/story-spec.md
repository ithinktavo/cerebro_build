# Story spec

For a product owner who writes stories and wants the developers and their tools to work from a spec. You name the story by its key. The tool reads it through the tracker's command-line tool, reads the project hub and a read-only clone of the repository at a named commit, and drafts one page in the vault with every line it proposed marked `AI:`. You edit the page in Obsidian, a review checks it, and delivery puts the same text into the repository as `specs/ALPHA-123.md` by pull request, with one comment on the story. From then on the repository file is the spec, and a revision changes it by pull request too: the open one while it is unmerged, a new one after the merge. The Specs switch in your profile ("Specs for my stories: yes") writes this ritual into your vault; this page says what to say and what to expect.

## What to say

- "Spec for ALPHA-123" drafts the spec from the story, the project hub, and the clone. "Spec for ALPHA-123: [what it must do]" adds your own lines. "Spec for ALPHA-123, from Microsoft 365 Copilot, 2026-11-09, [document link]: [three to five lines]" adds lines you got elsewhere, filed with that source.
- "Review the spec for ALPHA-123" prints the check table, pass or fail per check.
- "Deliver the spec for ALPHA-123" runs the review, then shows the branch, the file, the commit, the push, the pull request, and the story comment as one set.
- "Revise the spec for ALPHA-123: [what changed]" changes the repository file by pull request and answers the question on the story.

Say them to the tool opened on your vault with the clone added: `claude --add-dir ~/code/checkout-api`, `codex --add-dir ~/code/checkout-api`, or `copilot --add-dir=~/code/checkout-api`; [Connect your AI tools](../docs/02-connect-ai-tools.md) has the other routes. Use the key as your tracker prints it. "Which stories in Checkout Migration have no spec?" is a question in any words, answered from the project's recorded next-up query and the files in `specs/`. Record the two queries before you rely on the morning lines or ask "Which stories in Checkout Migration have no spec?"; "Spec for ALPHA-123" needs neither.

## What happens

1. The reads. The tool reads the story in full through the tracker tool in your session, description and comments included, and pastes none of it: `acli jira workitem view ALPHA-123` and `acli jira workitem comment list --key ALPHA-123`, `jira issue view ALPHA-123 --comments 10`, `gh issue view 123 -R example-org/checkout-api --comments`, or `az boards work-item show --id 123` with the comments through the REST route your `Library/YYYY-MM-DD Tracker Commands.md` note records. Then the project hub (Goal, Repos and deploy order, Decisions, Open questions, Specs) and its last three log entries; the repo hub, refreshed first when its commit moved or it is older than 30 days; and the clone after `git -C ~/code/checkout-api switch main` and `git -C ~/code/checkout-api pull --ff-only`: `git rev-parse --short HEAD`, the files already in the specs folder for the house shape, the paths whose names match the story's words, the test layout, and the PR template. What you say in chat or paste comes in with its source. A tracker tool that is not signed in gets one line; then say "Spec for ALPHA-123: [the story in your own words, plus its key, title, state, owner, and dates copied from the tracker], from Jira, [date]". The never-pasted rule is about the spec and the vault, not about what you tell the tool. An image or screenshot pasted into the chat is read for field names and shapes only, its values become placeholders, and it is never saved in the vault or linked from a spec; a tracker export (CSV, Excel, a board printed to PDF) is read like the story, for keys, titles, states, owners, and dates, pasted nowhere and never saved. With no clone, Where in the code reads `_left blank, needs the repository_` and the Verify lines name manual steps.

2. The draft and its marks. The whole draft is shown in chat with its path, `Projects/Checkout Migration/2026-11-09 ALPHA-123 Retry On Timeout Spec.md`, and the line it adds under Specs in the project hub. It opens with `# ALPHA-123: Retry on timeout` and keeps eleven headings in this order, none dropped and `none` allowed: Story (the story by URL with its state as of a date and the tool it is read with, such as "read with acli", the epic by URL, the repository, the reviewer by name and role, and the version line `r1, [date]`, `r0` while a draft, bumped on each revision; nothing copied from the story beyond key, title, state, owner, and dates); Why; Scope (In, Out); Acceptance criteria (opening with one line naming the commit the Verify lines were read at); Data and interfaces, opening with "Sample values only"; Where in the code, whose heading reads exactly `## Where in the code (AI proposal, read at commit [sha] on [date])`; Non-functional needs; Rollout; Open questions; Sources; Revisions. Each criterion is a block headed `### AC1` plus at most four words, such as `### AC1 Retry once on timeout`, then Given, When, Then with one observable result and exact values, and a Verify line naming the test path, the manual steps, or the metric and its threshold, proposed from the repository's test layout; three to seven of them, the ids never renumber, and a removed criterion is `### AC3 removed in r2` with no lines under it. Three kinds of line: a line you stated, in the story or in chat, carries no marker; a line read from the repository ends with its path and commit; a line the tool proposed starts with `AI:` until your yes. Sources lists your chat input as "[name] in chat, [date]"; there are no inline "said in chat" marks inside the spec body. Open questions are Q1, Q2, each with the owner, who is the one who answers it, the date asked, and the criterion it blocks or "blocks nothing"; a criterion a question blocks ends with `- Blocked by: Q1`. A customer, an account, a record, a log line, a production value, an internal hostname, an IP address, or a request, session, or trace id found in the story or a paste becomes a placeholder, and the reply lists what it left out. Under 80 lines, counted on the repository file, where the note's properties block and its Delivered, Built by, and Revisions lines do not count: a story whose spec needs more is two stories, and the tool says so and offers the tracker's command to create the second story instead of a longer spec.

3. Your yes. Nothing is written until you say yes. Then the note is created from the Spec template with its properties block (`type: plan`, `up` the hub, tags `spec` and the project's tag); the project hub gets its Specs line and its Notes in this folder line; the open questions go under the hub's Open questions with owner and date; the project log gets an entry; the AI notes are updated. Nothing is written to the repository or the tracker. In the same reply, say which proposals to keep: "Keep AC4 and the new setting, drop the rest, yes." The prefix comes off the lines you keep, the rest go or move under Open questions, and the note is created clean; what you did not mention stays marked, and you can drop the prefix yourself in Obsidian. The body is yours from then on.

4. The review table. "Review the spec for ALPHA-123" re-reads the note right before, or the repository file once delivered, plus the story's current title, state, and comments since the version date, and the clone at its current commit for every path in Where in the code and every name in Data and interfaces. It prints one row per check, pass or fail: every Then names one observable result with an exact value; every criterion has a Verify line naming a test path, manual steps, or a metric and its threshold; every criterion heading is AC plus at most four words; Out has at least one line; every path exists at the current commit, or the line marks it new; every open question has an owner and a date, and a blocked criterion says so; no `AI:` line remains outside Where in the code; nothing looks like customer data, a record, a secret, a hostname, or an id; three to seven criteria and under 80 lines, counted on the repository file; the story link resolves and its title matches; a criterion marked removed is skipped. Each fix is shown as before and after for one yes; once delivered, fixes go through "Revise the spec for ALPHA-123: [what changed]". A check that cannot run prints `not checked` with the reason, as the path and name checks do with no clone; with no tracker tool the title must match the pasted story; `not checked` does not decline a delivery, a fail does. The tool never approves a spec on anyone's behalf.

5. The delivery. "Deliver the spec for ALPHA-123" runs the review first and declines while a check fails. It reads the repo hub's Specs section for the folder, the file rule, the reviewer, and your access; checks your access now with `gh repo view example-org/checkout-api --json viewerPermission`; checks that `git -C ~/code/checkout-api status --short` prints nothing; and checks that `git -C ~/code/checkout-api branch --list spec/ALPHA-123` and `git -C ~/code/checkout-api ls-remote --heads origin spec/ALPHA-123` both print nothing, or switches to the existing branch and resumes from the push when it holds this spec's commit. With write access (WRITE, MAINTAIN, or ADMIN) it shows, as one proposal, the file as it will be committed, which is the note's body with the properties block dropped, its version line set to `r1, [date]`, and its Revisions section set to `r1, [date]: delivered for review`; then every command in order:

   ```
   git -C ~/code/checkout-api switch main   # go to the team's main copy
   git -C ~/code/checkout-api pull --ff-only   # bring it up to date; refuses if the clone was touched
   git -C ~/code/checkout-api ls-files specs/ALPHA-123.md   # must print nothing: never overwrite
   git -C ~/code/checkout-api switch -c spec/ALPHA-123   # make the spec branch
   git -C ~/code/checkout-api add specs/ALPHA-123.md   # stage the one file
   git -C ~/code/checkout-api commit -m "ALPHA-123: add spec"   # record it with that message
   git -C ~/code/checkout-api push -u origin spec/ALPHA-123   # upload the branch to GitHub
   gh pr create -R example-org/checkout-api --head spec/ALPHA-123 --title "Spec ALPHA-123: Retry on timeout" --body "Spec r1 for https://example.atlassian.net/browse/ALPHA-123. Review the criteria; the code comes later. Open: Q1." --reviewer <handle>   # open the pull request
   git -C ~/code/checkout-api switch main   # leave the clone on main
   ```

   One yes covers the set; each command still passes the tool's own prompt, and nothing runs before the yes. Expect one permission prompt per line; each names the clone path. `gh pr create` carries `--reviewer` only when the repo hub records a handle; with none recorded, the pull request opens without `--reviewer`, the body names the reviewer, and the set says so; the handle is added later with "My reviewer's handle for checkout-api is [handle]; update its hub". The folder the repo hub records wins over `specs/` when the team already keeps one. The `ls-files` check is made without regard to case; if it prints the path, the delivery stops, and a spec already in the repository changes through "Revise the spec for ALPHA-123: [what changed]". A pull that cannot fast-forward (a fast-forward pull only adds the team's new commits and refuses when the clone has changes of its own), or a clone whose status is not empty, stops the delivery with one line. If the push fails, the tool stops: the clone is on `spec/ALPHA-123` with the commit, and "Deliver the spec for ALPHA-123" again resumes from the push; it never deletes the branch, and never resets, restores, cleans, stashes, or force-deletes a branch. If `gh pr create` fails, the tool keeps going: it records the exact command under a fourth `AI-Memory.md` section, Waiting on tools (commands that have your yes but could not run), posts or prints the story comment with the branch and the file path in place of the URL, switches back, and writes the Delivered line of step 7 with the pull request pending. You never merge the spec pull request: the reviewer or the team does, under the repository's branch protection, the setting that lets nobody change main except through a reviewed pull request.

6. The story comment. After `gh pr create` and before the switch back, one comment goes on the story with the pull request URL and the file path, shown with the set and sent on the same yes. Before any story comment the tool reads who can read the story from the repo hub's `Story comments visible to` line (team, organization, or customers; a marked blank until you say or the tracker tool answers), says it, asks when the line is blank, and uses the tool's internal-comment option when it has one:

   ```
   acli jira workitem comment create --key "ALPHA-123" --body "Spec r1 for review: https://github.com/example-org/checkout-api/pull/456. After the merge: specs/ALPHA-123.md on main. Questions here as comments that open with the criterion id, as the Specs section of AGENTS.md says."   # comment create: check your version; add --help if it errors
   ```

   While the repo hub's Rulebook line says the repository's rulebook does not name specs, the comment ends after "the criterion id"; the clause "as the Specs section of AGENTS.md says" is dropped. For a GitHub issue it is `gh issue comment 123 -R example-org/checkout-api --body "..."`; for jira-cli, `jira issue comment add ALPHA-123 "..." --internal`, with its internal-comment option; for Azure DevOps, `az boards work-item update --id 123 --discussion "..."`; acli and az boards have no internal-comment option. A spec is as public as the repository it lands in and the story it is commented on. The story's description is never edited, and no label or status changes unless the project hub records one.

7. The vault bookkeeping. Reported, not asked: the note gets a Delivered line as its first body line, above the title: `Delivered [date]: [pull request or comment URL], specs/ALPHA-123.md. The repository file is what developers follow.`, or, while the pull request is pending, `Delivered [date]: branch spec/ALPHA-123 at [sha], pull request pending, specs/ALPHA-123.md. The repository file is what developers follow.`; the hub's Specs line quotes that state; the project log gets an entry; today's Log gets one `AI:` pointer line; the AI notes are updated. When the pull request is created later, or the file reaches the default branch without one, the tool rewrites the Delivered line and the note's Revisions lines to the URL or to `merged at [sha], no pull request`, and posts nothing twice. Then the paste-ready copy is printed for you, for Word, Loop, or a Teams post, with Where in the code dropped for readers outside the team. From here the note mirrors the repository file: after every revision the tool copies the file into the note as bookkeeping and keeps the Delivered, Built by, and Revisions lines.

8. The revision. A developer's question arrives on the story as a comment that starts with "Spec question, AC3:", and your morning names it. "Revise the spec for ALPHA-123: [what changed]" reads the repository file, never the note: on the open spec branch while the first pull request is unmerged, after `git -C ~/code/checkout-api switch spec/ALPHA-123` and `git -C ~/code/checkout-api pull --ff-only`, stopping if it cannot fast-forward; or at the default branch after a fast-forward once merged. It shows the diff: criteria keep their ids, a dropped one reads `### AC3 removed in r2` with no lines under it, the developer's question lands under Open questions in your words with the comment linked by URL, its answer goes on that line as `Answered [date]: [answer]`, or as `Answered [date] by me` with no URL when the answer is your own, and the Blocked by lines it held are removed, the version line is bumped to `r2, [date]`, and a Revisions line is added with the date and what changed and never a pull request URL: `r2, 2026-11-12: AC3 reworded, answers Q2`. Then the commit on the open spec branch, or `git -C ~/code/checkout-api switch -c spec/ALPHA-123-r2` from the pulled default branch and `git -C ~/code/checkout-api commit -m "ALPHA-123: revise spec (r2)"`, the push, a new pull request titled `Spec ALPHA-123: Retry on timeout, r2` or the open one updated (when no pull request exists yet, one pull request for the branch covers every revision and keeps the r1 title), the story comment `Spec answer, AC3: [one line], revised in [pull request URL].`, and the switch back to the default branch. Each is shown first and run only after your yes, as for a delivery; the request is not the yes. As bookkeeping, the tool mirrors the revised file into the note and appends the Revisions line with the pull request URL, the hub's Specs line changes, the project log gets an entry, and today's Log gets one `AI:` pointer line. A revision that touches a criterion a developer has already marked met in an open pull request says so in the comment. A code pull request never changes a criterion.

9. The story route. With read access (READ or TRIAGE from `gh repo view`), or with no clone, the delivery is one comment on the story, "Spec ALPHA-123, r1", carrying the whole spec as plain text, shown first. The Delivered line records the comment's URL, and the team's rulebook line makes the developer's first commit on the code branch add `specs/ALPHA-123.md` from it verbatim. A revision is a new comment, r2. acli sends plain text, and what Jira does with Markdown sent that way is undocumented; Jira's browser editor converts Markdown on the fly and accepts raw Markdown pasted in, so pasting the copy into the story there is the fallback; check the headings and lists after the paste. With no tracker tool installed at all, post the paste-ready copy on the story yourself, then say "Delivered ALPHA-123 as a story comment: [URL]". Ask the repository's owner for the write access any contributor has; branch protection keeps the default branch safe either way.

10. What stays out. The story's description and comments are read, never pasted; the spec is in your words. Customer records, production values, log lines, internal hostnames, IP addresses, and request, session, or trace ids never enter a spec: it names fields and shapes with made-up sample values, such as `customer-0001` and order 1234. Attachments stay in the tracker. The tool never edits `specs/` in a code pull request, never merges, never moves the story on its own, never sets or changes a git identity (a commit carries the one already configured on the computer, and with none configured the tool stops and says so), and runs no git write it has not shown. See [Keep it safe](../docs/05-keep-it-safe.md).

The developer's side is "Start on ALPHA-123" in the repository: the tool reads `specs/ALPHA-123.md` first, prints a plan with one line per criterion, stops at a blocked criterion and asks on the story, and its pull request says met or not met for each criterion with the test that proves it. The repository's own rulebook lines make every tool do that; see [Developer](../roles/developer.md).

## If your vault predates this ritual

A vault built with an older rulebook has a project hub but no Spec template, no Specs section, and none of the four phrases. Paste this with the brackets filled, to the tool opened on the vault with the clone added.

---

Write a spec for story [ALPHA-123]. It serves project [Checkout Migration] and lands in repository [example-org/checkout-api], cloned read-only at [path]. The team keeps specs in [specs/, or the folder it uses, or none yet]. The reviewer is [name, role, and GitHub handle if I know it]. My access to the repository is [write, read, or none].

1. Draft the spec from the story, read in full through its tracker tool with its comments and pasted nowhere, the project hub, and the clone at its current commit after a switch to the default branch and `git pull --ff-only`. Start every line I did not state and you did not read from the story or the repository with `AI:`; end a line read from the repository with its path and commit; list what I say in chat under Sources as "[my name] in chat, [date]". Replace anything that looks like a customer, an account, a record, a log line, a production value, a hostname, an IP address, or a request, session, or trace id with a placeholder and tell me what you left out; read an image, a screenshot, or a pasted export for field names and shapes only, and save or link none of it.

Check `git ls-files` without regard to case, and if it prints the file, stop: a spec already in the repository changes through "Revise". With write access, show me as one set: the branch `spec/[ALPHA-123]`, the file `[specs folder]/[ALPHA-123].md`, named after the key as the tracker prints it, holding the note's body with no properties block, the version line `r1, [date]`, and the Revisions section `r1, [date]: delivered for review`, the commit `[ALPHA-123]: add spec`, the push, the pull request titled `Spec [ALPHA-123]: [title]` with [reviewer] as reviewer, and one comment on the story: `Spec r1 for review: [pull request URL]. After the merge: [specs folder]/[ALPHA-123].md on main. Questions here as comments that open with the criterion id, as the Specs section of AGENTS.md says.` Drop the clause after "the criterion id" while the repository's rulebook has no Specs section.
